## 2026-10-14 轮换收编与重排（2.8 五批+末批全量审+走查，规格冻结归档）

**背景**：2.7 草稿评审探出「歇一轮在真产品兑现不了」——顺着挖出**三份取队实现互相漂移**的病根：前端发牌引擎认歇认连战、后端发牌闸只认字面队头、结算回流只认字面队头。实测两坑：跳过歇者的发牌上报被闸 422 打回（「发牌的人不在候场队首」，含歇者直发 200——前端想认歇反而必炸）；「待得最久的先下」的资历键从未被喂过（喂行手拼漏键，实际按名册序下人）。用户裁决取队算法全部收编后端单一真值，顺带立「重排这片」与轮询条件拉取。

**落点裁决**（全录 2.8 §8，这里记过程与被否项）：
- **方案 A 两处补丁 vs 收编**：补丁（结算认歇+发牌闸放行跳歇）修完三份实现还是三份，下次加取队规矩还要三处同步；收编后「谁上场」全站一个定义点。409 放大的质疑被三事实驳回：号跳冲突模型现状就有（13 处 bump 点）、收编后开片号跳从两次变一次、补片只碰空片。
- **「没计分就能改」不机器化**：比分在各手机本地（2026-10-09 裁决），服务器判定不了「有没有人开始记分」——安全模型维持「结算前都可手动改+责任人担保」，重排确认句把这句责任写进产品。
- **n1/n2/n3 补坑改「N 坑一次取齐」**：逐坑取 1 会让队首歇者跳过第一坑后被下一坑立刻捞上（歇白设）；一次取齐后边位 zip 落置与逐坑等价，跳过者确定整场不上。
- **补片降级不连坐**：评审吸收——纯函数先算计划挡计算面错，写回段 SAVEPOINT（begin_nested）挡落库面错，炸了只回滚补片段记 live_auto_fill_error，签到照常提交；不变量从「每次成立」降为「最终成立」（片留空，下一写动作自然重试+一键排阵兜底）。
- **豁免声明式**：收口处不记名单，四个端点各自声明不补片（改分重落/清扫取消/一键清/散场）——错忘方向从「忘了补（静默坏）」翻转成「忘了豁免（显眼）」。评审还揪出自查自相矛盾（写了「不回流不补片」清单却漏列改分重落），声明式后无名单可漏。
- **开场章（court_mark）治资历**：资历 bug 根在喂行不在排序——`_rotation_rows` 喂行单一源（键清单只存一处）+落位盖章（deal/结算回流/swap 入方，章值取落位时刻 total_seq），喂行漏键这类漂移从此绝根。

## 2026-10-13 微信快进建号（1.8 三批+走查修复，规格冻结归档）

**背景**：1.7 上线当日用户实测「授权回来还要填卡、已有手机号报占用、提示一闪而过」，拍板转向「优先服务新用户」——newfun 立 1.8（授权后直接成事、昵称电话后补），mawang 实现。开工前先收口工作区：两批咬合的在途改动按依赖序分两个提交（精简收编批 e636646 → 1.7 微信批 5e8d887），1.8 才有干净基线。

**落点裁决**（全录 1.8 §9 偏差，这里记过程与被否项）：
- **fast 参数 vs 独立端点**：选参数——认人门的 unbound 判定与 exchange 都是共享件，独立端点要复制前置链；登录页零改动靠 `fast=False` 默认值达成（4.7 找回面不快进护栏=后端默认值+前端来源位双保险）。
- **快进建号不发凭条**：凭条制是「未绑待落卡」用的；快进一次完成绑定（生而正式绑，§8 裁决 A），发凭条反而留一条可被别人核销的顶替种子。
- **收编挂点**：`redeem` 仅 recovery 支（takeover 是清场语义，挂收编会打架）+ `reset_password`（同属短信证明本人）；`login_password` 不挂（密码非短信，指路话术也只提短信）。收编与凭条并存时凭条先、收编后且幂等（凭条已把同一微信绑走，快进号 openid 已清，迁移自然空转）。
- **bind_phone 判定反转**：既有 send_code「查无账号不发码」，bind_phone 相反「有账号当场拒」——占用拒落审计账（`wechat_bind_phone_taken`），给将来「要不要立合并功能」留数。
- **指路不登出**：点「去登录页 ▸」只 navigateTo 不 logout 不清 token——收编靠 redeem 那一刻请求头里还活着快进号会话（current_account→adopt_from）；真「退出」= admitSession 换装落地。半途回退仍在快进号，非破坏。
- **验证官 Blocker 加一道门**：bind_phone 若不拦「已有手机号的账号」，被劫持的会话+攻击者自己的号=可换根号再走短信重置密码的持久接管——`phone_already_bound` 409 在核销验证码前挡下（验证码不烧、原号不动）。

**坑**：
1. **openid 换位的落序不变式**：同表两行换绑（清旧位+写新位）必须之间 `flush()`——SQLAlchemy 同表 UPDATE 按主键序批量执行，持有者主键更大时「写新位」先落 → UNIQUE 撞车。1.7 `_try_bind` 带着这颗雷没炸（既有测试持有者主键都更小），1.8 收编交错测试（老账号 id=1 < 快进号 id=2）首踩。已抽 `_rebind` 单一正路（注释写明「新增换位路径一律走这里」）。
2. **`wechat_bound` 只在发钥匙回话一次性下发**：`/auth/me` 与本人档案视图原本没有这格——重启后已绑用户的「微信已绑定」行会消失（画面说谎）。本人视角 view() 补一行；写技术设计时「1.7 已下发」是想当然，实查打脸。
3. **单槽 toast 顶替**：ui.toast 是单槽（2200ms 自熄，后来者直接覆盖）——随机名回执先发、续办动作话紧随（API 往返几十 ms），名字句完全看不见。修法=动作话先说、`setTimeout(sayName, 2400)` 排队补报名字；2400 的余量按 AppToast 2200+本地 RTT 算，弱网下动作话可能被名字句提前 ~百 ms 顶掉（可接受：动作结果在名单/状态条永远可见，名字只在 toast 有）。
4. **补绑面板跨身份残留**：mine 是 tab 页不销毁，面板展开态+409 错误行在收编换身份/退登后照样挂着（旧提示在新身份下误导）——`watch [isGuest, maskedPhone]` 变化即收面板清态。tab 页组件的弹层状态都要过一遍「身份变了还在不在」的审视。
5. **假通道 build_url 恒发 code=wx_dev**：多微信号走查（收编要「另一个微信」）要么改通道要么拦截——本次走查用页内 XHR patch 改写 /wechat/url 响应的 code（`wx_adopt`/`wx_late`），state 双闸不受影响。下次多号走查直接抄。
6. **走查先探新端点再开跑**：16589 被上次走查的旧进程占着，我的实例起失败静默退出，curl 通的是旧代码（无 fast 参数→快进恒不触发，白跑一轮）。起架子后先 `curl` 新端点确认形状（401/404 之别）再走。
7. **uni-input 受控值 fill("") 清不干净**：Playwright fill 空串后 uni 的 v-model 仍持旧值（快进号吃草稿名「微信测试员」建的）——走查要干净输入直接 `localStorage.removeItem` 草稿键（mieball.cardDraft）后重挂组件，别跟受控输入搏斗。
8. **IAB 点 uni 组件偶发 actionability 卡死**：getByText 明明 count=1 却 timeout（遮挡判定误报），`cua.click` 坐标路径 + 截图定位是可靠退路；`force:true` 点击对 uni 事件桥时灵时不灵。

## 2026-10-12 微信钥匙点亮（1.7 规格+前后端实现，资质到位即上线）

**背景**：用户告知认证服务号资质当天大概率办下来，指令「前后端准备就绪 + newfun 立 1.7」。1.6 §4.12 立的框架（给位不给死按钮）本轮兑现。

**落点裁决**（评审四角色全过，细节全录 1.7 §8）：
- **绑定两档制**：`wechat_verified` 完全镜像 `device_keys.verified`——验明正身时刻绑=正式绑（微信进门=验明正身，杀未验证钥匙）；纯建号顺手绑=顺手绑（真主人验明正身时自动解开，D4 的微信面）。这是把 1.6「绑定时验过手机号」承诺与「建号不验短信」的既有取舍缝起来的唯一解。
- **微信出口接管不清绑定**：短信/密码接管清（短信证明的是号码、号码可易主），微信接管不清（绑定本身就是进门凭证，清了本人下次一键就废）——C3 起草时漏了这层不对称，代码核对员抓的。
- **凭条顶替换绑**：wechat_login 恒发 bind_token（绑着的也发）——一个微信想搬到别的账号，下一个验明正身凭它顶替（旧绑定当场解开）；同账号重绑只升不降。
- **换锁（忘记密码重置）不清正式绑**：设备钥匙全作废但微信这把经真身验证的钥匙留着——被盗密码场景本人多条活路；被盗微信反过来走短信接管断开。追认暗面已录 1.7 §8（这条实际在解释 1.6 §4.10 冻结句的字面）。
- **绑定失败静默跳过且不说「已绑上」**：响应只在真绑上时带 `wechat_bound`（auth.py `_session_out` 单点），前端 toast 跟着定值走——评审员抓的「提示撒谎」洞。
- **假通道**：`wechat_provider=fake`（默认，凭证即身份号=code 直接当 openid）对齐短信 console 假发送器先例；real 未配 AppID/Secret 通道按 wechat_off 关死。**上线必设 `MIEBALL_WECHAT_PROVIDER=real` + `MIEBALL_WECHAT_APP_ID/SECRET`，假通道上生产=免认证放行**（config 启动有警告印）。
- 前端**转场包**：跳微信授权页是整页跳转，SPA 内存态全丢（pendingAfterLogin 自认「内存非持久」）——出发前把占卡手机号/挂起快照/回跳落点/防伪 state 存本机（utils/wechat.ts），回来登录页 onLoad 收 code 消费；挂起动作接着办的承诺不因换通道打折。

**坑**：
- SQLite `ALTER ADD COLUMN` 加不了 UNIQUE：微信登记位唯一索引改走启动补建（main.py `_ENSURE_INDEXES`，IF NOT EXISTS 幂等）。模型里**不能**同时声明这个索引——删列重建路径（`_drop_legacy_columns` 先 RENAME 再按模型建新表）会与改名表上的同名索引撞车，test_schema_migration 直接红（代码核对员在评审中途撞见的 293/1 就是它）。
- `ruff format app` 会顺手重排没动过的旧文件（keys.py 被 +12/-3）——formatter 只对触过的文件跑，误伤要 `git checkout` 还原。
- 旧 session-store 断言按精确参数比对，五个动作加 bind_token 槽位后全要补第四参 undefined——参数槽位变更是全量断言债。

**验证**：后端 294 绿（test_wechat 16 例全矩阵：通道开关/凭条过期/两档升降/顶替/三种占卡拒/接管·换锁·注销清场/存量库列迁移）；前端 269 绿（wechat.test 12 例 + session-store 微信 5 例）/vue-tsc 净/prettier 过/触文件 ruff 净（B008 为全仓预存惯例）。真机微信联调待资质配置后补走查。假通道浏览器全链走法：DevTools 手机模式把 UA 换成带 MicroMessenger 的点按钮即走通（假地址自带 code=wx_dev 原路跳回）；或控制台先种转场包 `uni.setStorageSync('wechatAuthCtx',{state:'s1',back:'/pages/meet/meet',ts:Date.now()})` 再开 `#/pages/mine/login?code=wx_任意身份号&state=s1`（冷开带 code 过不了防伪闸——state 对不上属预期拦截）。

**坑**（按踩到的顺序）：
1. **slice_commit 闸 5 的批行路径是精确字符串匹配**：技术设计落点清单写 `src/sandbox/data.ts`、提交清单传 `frontend/src/sandbox/data.ts` → 「不在任何批清单里」硬拒——批行路径必须写 git 相对路径（带 frontend/ 前缀）。计划外文件先补录批行再重跑，别跟闸较劲。
2. **uni-app @tap 在 H5 是框架合成事件，evaluate 的 element.click() 触发不了**：走查给凯文签到用合成 click 没签上、提示行卡在第 3 条——一度误判成步进 bug，真凶是点击手法；playwright 真实点击（有 mousedown/up 序列）正常触发。走查点自绘组件钮一律 playwright click，evaluate click 只留给遮罩这类 pointer-events 特殊层。
3. **uni 弹层是 translateY 移出屏幕而非 display:none**——innerText 把隐藏抽屉内容也算进去，按文本存在性判「谁在场/抽屉开没开」会假阳（老金明明到了却「搜不到」、关了的抽屉还有凯文未到）。判定一律 offsetHeight>0 + 类名（.sheet.on/.mask.on）。
4. **hash 路由 goto 同 URL 不重跑冷启动**：清库重灌后 goto live 页还是旧真局画面（Pinia 内存态没洗）——必须 tab.reload() 整页冷启动，onLoad 分发与认人才重跑（与 2.6 坑 3 同族）。
5. **format.test.ts 存量时钟闪失（连续三批取证）**：相对时间用例在北京晚 21–24 点跑必挂（「今天/明天」跨日翻转），凌晨开发机上反复出现——三批各自 stash 干净树实证与本批无关。修法便宜（断言只看字段有无），建议单独批处理掉，别再让每个实现工重复取证。
