## 1. 这是要解决什么问题（必填，人话）

- 现在的毛病：系统出事的记录只活在终端黑窗口里，窗口一关就没了；线上出事只能靠球友口述「页面白了」，对不上人、找不到事；谁改了比分、谁点的散场，过几天就说不清；以后改了算分或摊费的规矩，历史这笔分、这笔钱当时怎么算的没法解释。
- 一句话成功画面：出事时球友报一个短编号，你拿号一搜就是完整案发现场；想知道谁动了什么，按球局号一翻全有时间有人的记录；老账拿「当时的比分 + 当时的版本记号」原样能推出来——而这一切不拖垮系统本身。

## 2. 给谁用（必填，按角色写）

- **项目主人**（你自己）：排障有据（错误号直达案发现场）、追责有痕（按球局翻动作审计）、复盘有本（规则版本记号）、日常省心（两条快捷查日志指令）。
- **球友**：只在两处沾边——意外出错时提示里有个可以念给你的编号；按你指引点一下「复制诊断日志」发给你。除此之外感觉不到这个功能存在。
- **组织者/管理员**：不直接使用本功能；他们的操作会被自动记进审计，无需做任何额外动作。
- 不为任何角色服务的部分：无（访问流水是给你排障用的对照面，服务项目主人）。

## 3. 用户故事（必填）

- 作为项目主人，我想让系统的记录自动写进文件、按天归档、只留最近 14 天，以便终端窗口关了记录也不丢、磁盘也不会被撑爆。（服务 §1 全部）
- 作为项目主人，我想让每次意外出错都生成一个全站不重复的短编号、弹给球友，以便球友报号、我搜号直达出事的那一行。（服务问题：对不上报错球友）
- 作为项目主人，我想让几乎每个业务动作都自动留下「几点、谁、在哪个局、干了什么」的审计记录，以便追责和复盘时不用人肉拼零散信息。（服务问题：谁动了操作说不清）
- 作为项目主人，我想让战力明细和账单落账时打上当时的规则版本记号，以便日后调参也能原样还原「当时这笔分/这笔钱怎么算的」。（服务问题：历史依据算不清）
- 作为项目主人，我想让现场页的悄悄刷新正常时一个字不写、慢过一秒自动亮警告，以便有用记录不被刷屏冲掉、性能劣化能提前看见。（服务问题：不给系统添堵）
- 作为项目主人，我想让球友手机上的最近操作轨迹能一键复制发给我，以便服务器日志毫不知情的手机卡死、白屏也能还原现场。（服务问题：手机端的问题服务器日志看不见）

## 4. 输入 / 输出场景（必填，文档核心）

### 场景 4.1：球友撞上意外错误，拿到编号
- **身份**：球友
- **前提**：正在用 app 的任意功能（记分、报名、看页……）
- **操作**：点了一个动作，系统内部出了意料之外的错（不是「比分还没记完」这类系统自己能说清的错）
- **结果**：界面弹一条提示，大意是「出了点问题，请把编号 ERR-8F2B 发到反馈群或告诉群主」；编号是短的一串，念得出、抄得下；球友关掉提示后别的功能照常用。
- **禁止**：不给球友看大段英文报错原文；不因这一个错让整个页面白屏或卡死；系统自己能说清的业务错误（界面本来就有中文提示的那种）不带编号；断网、超时这类网络失败也不带编号——维持「网络不给力」这类中文提示，不吓人。

### 场景 4.2：拿编号查案发现场
- **身份**：项目主人
- **前提**：球友把编号报给你了
- **操作**：在服务器上用查日志的快捷指令输入这个编号
- **结果**：几秒内列出这条错的完整记录——什么时候出的事、在哪个球局、当时谁在操作、用的什么端（手机网页/小程序）、系统内部到底哪一步怎么错的完整过程；顺带把前后几分钟同一个局的相关事件也列在一起。查不到这个编号时，客气地说「没有这个编号：可能抄错了、已过 14 天销毁、或当时没写成」，不报错不崩。
- **禁止**：不需要翻一堆文件人肉拼。

### 场景 4.3：按球局翻动作审计
- **身份**：项目主人
- **前提**：有人问「那局的比分怎么改过」「谁点的散场」，或你自己复盘
- **操作**：用查日志的快捷指令输入球局号（或调预留的读取口）
- **结果**：这个局从发局到散场的动作按时间排成一条线：几点谁发的局、谁开的账、谁被设成管理员、谁确认的比分结果、谁在结算窗改过比分、谁确认了转款和收款、谁点的散场；连报名、签到、发牌、空降、带访客、邀请、留意向这些常规动作也在。每条都带时间和操作人。审计可查的窗口就是最近 14 天——追责请趁早。
- **禁止**：审计记录里不许出现手机号明文和登录钥匙。

### 场景 4.4：老账复盘——这笔分/这笔钱当时怎么算的
- **身份**：项目主人
- **前提**：几个月后你改过算分或摊费的规矩，有球友问起之前某场的分或某笔钱
- **操作**：查看那场对局的战力明细或那笔账单的记录（账单在 app 里翻得到；战力明细眼下没有界面入口，这步直接查记录）
- **结果**：明细上带着落账当时的规则版本记号，每个记号都能对上当时的那套算法规矩；拿「当时的原始比分 + 当时的版本记号」能原样推出当时的结果，不因后来调参而说不清。
- **禁止**：球友界面上不显示版本记号（不吵人）；已落的老账不回头补记号（按当时的文档查）；凡改动会影响算分或摊费结果的规矩，落新账时必须换一个新的版本记号——不许沿用旧记号记新算法。

### 场景 4.5：现场页开着也不刷日志
- **身份**：球友（他感知不到，这条是替系统写的）
- **前提**：现场页开着，页面每隔几秒自己悄悄刷新画面
- **操作**：挂上三个小时
- **结果**：画面一切正常时，日志里一行刷新记录都不留；哪次回应不正常（服务器出错或超时），那条失败被记下（时间+球局+谁）；哪次回应慢过一秒，记一条慢的警告并写明等了多久。手机自己断网时服务器看不见这回事——那段时间的轨迹靠手机上的诊断日志兜底（见 4.6）。
- **禁止**：正常刷新不许刷屏日志。

### 场景 4.6：球友手机卡了，黑匣子还原轨迹
- **身份**：球友 → 项目主人
- **前提**：球友手机上偶发卡死、白屏或断网，服务器上的日志对此毫不知情（手机重启、重开 app 后轨迹还在，别慌）
- **操作**：你让球友打开「我的」页，点「复制诊断日志」，粘贴发给你
- **结果**：粘出来的是一段可读的文字——最近二三十步轨迹（几点进了哪个页、对结果有影响的核心动作：记分、确认、报名这类）、最近一次报错的样子（带着当时的编号）、手机和版本信息；手机号、登录钥匙这类敏感信息自动打码。
- **禁止**：不记球友在输入框里打过的字（如聊天内容、手机号输入）。

### 场景 4.7：日志自己也不能拖垮系统
- **身份**：全体用户（系统自保）
- **前提**：磁盘快满、或日志文件写不进去
- **操作**：（系统自己处理，无人操作）
- **结果**：宁可当条日志丢掉，也绝不让打球的功能卡住或报错；现场记分、报名、结算一切照常。等日志能重新写时，第一件事补记一条「某时段丢了 N 条记录」的缺口标记——让「没记上」和「没人操作过」永远分得清。
- **禁止**：不因日志的故障连累业务功能出错。

### 场景 4.8：老日志自动销毁
- **身份**：系统
- **前提**：某天的日志存满 14 天
- **操作**：每天半夜十二点（按北京时间）切换新文件时顺手检查；哪晚服务停着错过了，重启时补做一次
- **结果**：超过 14 天的日志文件和审计文件自动销毁，磁盘占用永远封顶在最近 14 天的量；规则版本记号不受影响（它跟着战力明细和账单本身存，永久保留）。
- **禁止**：日志无限堆积占满磁盘。

### 场景 4.9：为以后的管理员界面预留读取口
- **身份**：项目主人（面向未来）
- **前提**：以后想做个界面来翻审计、搜错误，而不是每次敲指令
- **操作**：用你手里那把专属钥匙，把「按球局翻审计」「按编号查错」两条查询各跑一遍
- **结果**：两样都查得到，以后的管理员界面直接接这两条查询用，不用重做；这把钥匙怎么签发、系统怎么认，动工时设计。
- **禁止**：现在就做界面；口子现在不对其他人开放。

### 场景 4.10：刚上线，什么都没发生过
- **身份**：项目主人
- **前提**：服务新装好，没出过错、没人在里面操作过
- **操作**：用快捷指令查日志或查审计
- **结果**：返回空（客气地说「没有记录」），不报错不崩；日志文件里只有服务启动的几行。
- **禁止**：空的时候不许把查询本身搞挂。

## 5. 验收标准（必填，可勾选）

- [x] **正常：动作落审计** ✅ —— 对应故事 3

  → 验证：人为制造一次意外出错，球友端提示出现 ERR 开头短编号；拿编号一搜，完整出错过程（含一步步的调用轨迹）整段带出，顺带列出同局前后事件。

  → 验证：现场页正常刷新多分钟日志零刷新记录；服务器回一次不正常回应，失败那拍带着几点/球局/谁落进日志。
- [x] **正常：慢回应警告** ✅ —— 对应故事 5
  → 验证：人为造一个慢过一秒的回应，日志出现警告并写明等了多少毫秒。
- [x] **正常：规则版本记号** ✅ —— 对应故事 4
  → 验证：结束对局与生成账单后记录各带版本记号；球友界面上看不到记号；把版本换新后再落新账——新账新号、旧账原号原样不动（新旧并存的场景有专门的核对）。
- [x] **正常：诊断日志** ✅ —— 对应故事 6
  → 验证：浏览器实走——游客也能看到并点「复制诊断日志」，粘出来的文字含最近轨迹（进了哪页、报了什么错）、最近报错与手机信息，无明文手机号；复制不成功时提示「再试一次」。
- [x] **正常：读取口预留** ✅ —— 对应场景 4.9
  → 验证：带上专属钥匙两条查询各跑通（按局拉到事件、按编号查到现场）；不带或带错钥匙都被拦下。
- [x] **空状态** ✅：新装服务查日志/审计
  → 验证：空查询得「没有记录」；不存在的编号得「可能抄错了/已销毁/当时没写成」；刚装 app 点复制得「暂无轨迹+手机与版本信息」短文字。三项均实测。
- [x] **出错：业务错误不带编号** ✅ —— 对应场景 4.1 禁止
  → 验证：业务错误维持原中文提示、无编号；断网提交看到「网络不给力」、同样无编号。
- [x] **出错：日志写不进去不连累业务** ✅ —— 对应场景 4.7
  → 验证：把日志目录指到一个写不进的地方，报名、健康检查照常好用；恢复可写后第一笔补上「某时段丢了 N 条」的缺口标记。
- [x] **边界：14 天销毁** ✅ —— 对应场景 4.8
  → 验证：15 天前的旧文件过切割点被销毁、按天各归各、旧文件在位；服务重启补做一次切割与清理；13 天在可查窗口内、15 天不在。
- [x] **边界：敏感信息脱敏** ✅ —— 对应场景 4.3/4.6 禁止
  → 验证：带手机号的出错过程、审计明细、诊断包逐一翻过，明文手机号与登录钥匙一处都没有（自动变星号）。

## 6. 边界与非目标（必填）

- ❌ 明确不做：
  - 出错主动推送告警（推送/短信通知开发者）——自用规模，球友报号足够。
  - app 内的日志/审计查看界面——只在服务器上预留读取口，界面以后单独立项。
  - 运行时调整日志详略的开关——出问题时改一下启动配置重启即可，不做界面开关。
  - 老数据回填规则版本记号——已落账的按当时文档可查。
  - Elo 娱乐轨单独版本记号——同一场的战力明细上已有版本，能推出当时是怎么算的。
  - 审计不记这些动作：改轮换方式/分制、换人、歇两轮/连战、账号注销、改局、改头像名片——过程性调整与自己动自己的动作，结算与账单有最终数。
  - 逐分记录不单独审计——比分要点确认才生效、随结算窗落定，落账时「谁确认的、最终几比几」进审计，战报本身就是记录。
- ✅ 做但降级（自用够用即可的部分）：
  - 查日志就两条快捷指令（按球局号、按错误号），不做更花哨的分析台。
  - 预留的读取口眼下没有任何使用者（只服务以后的管理员界面）——它是第一顺位可砍项，砍了不影响本规格其余一切。
  - 登记义务算明文规矩：以后上线新动作、新页面，必须同步登记进审计清单和诊断日志的核心动作——不登记它就静默漏记，这条债只能靠人记。
  - 每次操作的访问流水先全记上（一天几千行、不足 1MB，无负担），日后量真不合适再删。
  - 日志详略靠启动时的配置定档，分档就粗细两三档。

## 7. 附录（前端必拼，后端/数据按需，同样人话）

### 附录 A：前端行为

**A1. 屏幕清单**
- 「我的」页：新增一个「复制诊断日志」按钮（游客也可见可点）；除此之外没有任何新屏幕。
- 出错提示（现有提示条的自然延伸）：意外错误时提示文案里带编号；业务错误维持原中文提示，不加编号。

**A2. 每屏的状态**
- 复制按钮：本地还没有任何轨迹时（刚装 app 就点），复制出来的是「暂无轨迹 + 手机与版本信息」的短文字，不报错；复制动作本身失败时提示「复制没成功，再试一次」。
- 出错提示：编号出现即完整（一串短号），不需要球友补任何别的信息；提示可关闭，关掉后不影响其他功能。

**A3. 操作与响应**
- 点「复制诊断日志」→ 内容进剪贴板 → 提示「已复制，发给组织者就行」；误点无任何副作用（纯复制，不发任何东西）。
- 黑匣子在后台静默记：进了哪页、出了哪页、对结果有影响的核心动作（记分、确认、报名这类，与审计清单同一套），以及每次报错（报错里带当时的编号）；只留最近二三十步，老的自动滚掉；不记输入框里打过的字。

**A4. 数据从哪来**
- 出错提示里的编号必须是系统出错时给定的那个，画面只负责显示，不自己造号、不改写。
- 诊断日志里的手机与版本信息、打码规则由本机固定逻辑处理；操作轨迹是本机自己记的，不依赖网络。

### 附录 B：后端行为

**B1. 触发与响应**
- 每个动作进门，系统自动贴好「谁（记操作人的用户编号，不是手机号）、在哪个局、用什么端」的标签——业务功能不用自己操心记录这件事。
- 审计在动作成功后补一笔，不耽误用户的操作：用户先看到自己操作的结果，记录随后落进文件。
- 日志文件与审计文件分开存（出错的流水和动作的账本不混一个文件），每天的文件半夜十二点（北京时间）切换新的一份。

**B2. 失败时用户看到什么**
- 日志或审计写失败：用户完全无感，业务照常（丢日志不丢功能）。
- 现场页悄悄刷新失败：手机自己静默地在下一拍再试，不打扰球友；服务器看得见的那类失败（回应不正常、超时）才进日志。
- 意外错误：球友看到带编号的提示；完整过程记录已在日志里，编号和记录一一对应。

**B3. 量放大 100 倍时**
- 正常刷新零记录的规矩保证了日志量不随在线时长爆炸；100 倍人在线也只是失败和慢的记录多一些。
- 审计按动作条数增长（不含正常加分），100 倍规模一天也就几万行；按球局号/编号查询仍应在几秒内出结果。
- 磁盘占用恒定封顶（14 天），不随时间增长。

### 附录 C：数据行为

**C1. 数据清单**
- 运行日志（按天的文件）：意外错误（含编号与完整过程）、慢回应警告、回应不正常的失败、每次操作的访问流水（谁、什么动作、多久、成败）、「某时段丢了 N 条记录」的缺口标记。
- 审计记录（按天的文件，与运行日志分开）：动作名 + 时间 + 操作人 + 球局——记的动作：发局、开账、设/撤管理员、确认结束对局（含最终比分）、结算窗改比分、取消对局、未完对局全部取消、散场、账单的转款确认与收款确认、撤局、恢复、锁定必打、订场登记、清空订场、补填总价、报名、退出、签到、发牌、空降、带访客、邀请、留意向、删意向。
- 规则版本记号：战力明细和账单落账时打上，随明细与账单本身永存（不受 14 天限制）。
- 黑匣子（球友手机本地）：最近二三十步轨迹（页面进出+核心动作）+ 最近一次报错（带编号），滚动覆盖。
- 错误号：意外出错时生成的短号，14 天保留期内不重复、位数做成基本不撞，与日志记录一一对应。

**C2. 谁能看 / 改 / 删**
- 服务器上的日志与审计文件：只有项目主人（能碰服务器的人）可见。
- 预留的读取口：只认项目主人手里那把专属钥匙（怎么签发、怎么认，动工时设计）；其他人调不动。
- 黑匣子：只存在球友自己手机上，导出（复制）由本人主动操作，不自动上传任何地方。

**C3. 留多久、删了会怎样**
- 运行日志与审计文件：保留 14 天，到期自动销毁，销毁后不可恢复（追责请趁早）。
- 规则版本记号：永久，随战力明细与账单走。
- 黑匣子：滚动覆盖最近二三十步，关 app 不清空、换手机不带走。
- 手机号与登录钥匙：不进任何日志、审计、诊断包——这不是保留期问题，是根本不落。

### 评审期裁决（2026-10-09，四角色评审后）

- **审计通道对齐记分本地化现状（评审修正，用户放行 ✅）**
  - 规格 1.0 稿把「撤回一分/清零」当服务器的动作——实际它们是手机本地的操作（记分本地化后不经过服务器），服务器上的审计看不见。
  - 修正：审计记「确认结束对局（含最终比分）」+「结算窗改比分」两个真实通道，比分真相的追责链完整；手机侧的逐分轨迹由诊断日志（黑匣子）兜底。
- **黑匣子轨迹记到多细：核心动作级（用户裁定 ✅）**
  - 选项 A：页面进出 + 对结果有影响的核心动作（已选——「只记录核心动作」；核心动作与审计清单同一套，登记义务明文化进 §6）。
  - 选项 B：每个按钮都记——复盘最细，但每个新按钮都要记得埋点，是终身维护税（产品顾问预警）。
  - 选项 C：只记页面进出——最省事，但现场页里点过什么分不清。
- **发局记入审计（用户裁定 ✅ 记）**
  - 局的出生影响名单与后续一切动作；同场裁定「歇两轮/连战」「改头像名片」不记（过程性/自己动自己，同换人档）。
- **网络类失败不弹编号（评审补定，用户放行 ✅）**
  - 断网/超时维持「网络不给力」类中文提示，不生成编号——否则信号差的一晚全馆球友被编号轰炸；手机断网服务器看不见，心跳静默只记服务器看得见的失败（回应不正常/超时）。
- **版本记号变更规矩补严（评审补定，用户放行 ✅）**
  - 两位评审员同击单向门：什么算一次版本变更原本没定义、验收测不出记号随改规矩而变，而规格又禁止回填——错一次永久补不回。
  - 补：凡改动影响算分/摊费结果的规矩，落新账必须换新记号；验收加复算（新账新记号、旧账不动、凭旧记号复算出同样的数）。

### 实现期裁决与偏差（2026-10-10 实现回写，此后冻结）

- **审计落位更精确**：「动作成功后补一笔」落为「服务办完事、把结果交还用户之前」记——用户先看到操作结果不受耽误；办砸了的动作（界面弹中文提示的那种）自然一条不记。
- **黑匣子「核心动作」落为全部写动作**：全站每个提交类动作（报名、记分、确认……）自动进轨迹，与审计清单同一套语义，不用逐个登记；页面只记「进了哪页」不记「出了哪页」——退出时刻在应用被强杀时本就抓不到，进的先后足以还原轨迹。
- **手机断网的服务器盲区**：手机自己断网服务器看不见（现状如此），那段时间的现场还原靠手机上的诊断日志兜底——与 4.5/4.6 的分工一致。
- **连续同类的错只记一条**：现场页每 3 秒的悄悄刷新在断网时会连续失败，诊断日志对连续同码的报错去重，保证轨迹不被刷掉——这条是走查前验收抓出来的补丁。
- **读取口钥匙**：环境变量里配一把专属钥匙、查询时随请求头带上；不配置 = 读取口关闭。钥匙怎么签发是动工期设计点的兑现。
- **错误号六位**：十四天保留期内约四千次意外错误内基本不撞——自用量级安全；真撞了以先入库的那条为准。
- **电脑浏览器里复制诊断日志可能失败**（剪贴板权限），提示「再试一次」；手机端原生剪贴板不受此限。浏览器实测恰好验证了失败分支的提示。
- **改局不记、逐分不记的补充说明**：逐分记录是手机本地的操作（记分本地化），服务器审计看不见——现场还原由诊断日志兜底，与评审期「审计通道对齐记分本地化」裁决一致。
- **访客冷启动会占诊断日志一条报错**：游客打开 app 时系统照例问一次「你是谁」、得到「未登录」的答复——这是预期中的失败，会被轨迹记一条；连续同码去重保证它只占一条，可接受。
